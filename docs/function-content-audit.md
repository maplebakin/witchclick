# WitchClick Function & Content Audit — 2025-10-05

## Snapshot
- **Scope.** Reviewed ingestion scripts, shared server libraries, Astro runtime utilities, admin authoring surface, and generation tooling to understand how specs become Markdown, how runtime functions serve pages, and how prompts guide new content.
- **Method.** Traced the ingest → normalize → persist flow, inspected UI + CLI touchpoints, sampled entity/blocks loaders, and skimmed representative content assets to map dependencies and guardrails.
- **Overall finding.** Core pipelines are cohesive—`prepareSpecForPersistence` enforces schema + structural rules and is reused by CLI, API, and admin flows—yet a handful of helper functions and content generators still rely on divergent assumptions that can drift as the product evolves.【F:server/lib/specPreparation.js†L139-L248】【F:scripts/ingest.mjs†L21-L123】【F:src/pages/admin/index.astro†L831-L903】

## Strengths Observed
- **Single source of ingest truth.** Both the CLI (`npm run ingest`) and admin UI call into `prepareSpecForPersistence`/`persistPreparedSpec`, so normalization, slug conflict resolution, and entity stub creation are uniformly applied regardless of entry point.【F:scripts/ingest.mjs†L60-L123】【F:server/lib/specPreparation.js†L139-L268】
- **Runtime loaders respect modern + legacy paths.** `loadAllPosts()` scans `src/content/posts` before falling back to `content/posts`, sorts by derived dates, and exposes helpers for pagination, reading-time estimation, and hero copy, which keeps the front page logic straightforward.【F:src/utils/posts.ts†L42-L183】【F:src/pages/index.astro†L8-L115】
- **Author tooling surfaces canonical feedback.** The admin page posts specs to `/ingest?dryRun=true`, echoing normalization notes and warnings, so editors preview the exact Markdown + cautions they will ship without bespoke validation logic.【F:src/pages/admin/index.astro†L831-L918】
- **Blocks + settings validation.** Zod-based parsing for evergreen blocks and custom validation for `settings.json` prevent malformed marketing copy or analytics toggles from crashing renders and provide safe defaults for canonical URLs, disclosures, and scripts.【F:src/utils/blocks.ts†L5-L69】【F:src/utils/settings.ts†L1-L111】

## Improvement Opportunities
### Runtime & Pipeline Functions
1. **Centralize slug + path helpers.** Three separate modules implement their own slugification (`deriveSlug`, `slugify`, `normalizeSlugCandidate`), each with slightly different regex rules, which can create mismatched URLs between ingest, runtime lookups, and logging.【F:src/utils/posts.ts†L55-L58】【F:server/lib/specPreparation.js†L27-L35】【F:scripts/ingest.mjs†L348-L419】 Extract a shared `slug.ts` utility and reuse it across ingestion, loaders, and admin logging to prevent subtle divergence.
2. **Expose draft/visibility filters in loaders.** Post ingestion always writes `includeAds`, `includeKofi`, and `publishedAt`, but `loadAllPosts()` does not respect a `draft` or `published` flag when sorting/returning posts, so staging content appears publicly once the file exists.【F:server/lib/specPreparation.js†L207-L235】【F:src/utils/posts.ts†L83-L117】 Consider honoring `data.draft === true` (or similar) to keep unlaunched content out of listings without deleting files.
3. **Unify directory resolution across tooling.** The ingest script dynamically picks `src/content/posts` or `content/posts`, yet `genprompt` only inspects `content/posts` when deduping titles, so prompts may recommend slugs that already exist in the content-collections folder.【F:scripts/ingest.mjs†L21-L123】【F:tools/src/genprompt.ts†L56-L68】 Share the directory resolution logic (or consume `loadAllPosts()`) so generators see the complete catalog.
4. **Add typed parsing for curse frontmatter.** `loadAllCurses()` trusts any `gray-matter` output and only normalizes headings via regex, leaving room for missing invocations, malformed tags, or empty sections to slip through and crash templates.【F:src/utils/curses.ts†L39-L105】 Mirror the post pipeline by defining a Zod schema for curses and surfacing validation warnings in admin/CLI tooling.
5. **Tighten evergreen block cache invalidation.** `readEvergreenBlocks()` caches on `mtime` but does not consider JSON parse errors once logged, meaning a broken file causes subsequent reads to stick to the empty fallback until the process restarts even after the JSON is fixed.【F:src/utils/blocks.ts†L37-L63】 Reset the cache when parsing fails (instead of storing `{ testimonials: [] }`) or expose a manual bust helper for live previews.

### Content Creation Tooling & Specs
1. **Modularize the master prompt.** `buildMasterPrompt()` assembles a 200+ line string with interleaved prose and schema docs, which is difficult to diff or localize as requirements change.【F:server/lib/promptBuilder.js†L1-L192】 Break the template into reusable markdown/JSON fragments (e.g., arrays of paragraphs or tagged template literals) so editors can update tone or structural rules without navigating a monolithic blob.
2. **Surface content analytics in prompt inputs.** The generator already reads affiliate keys and existing titles, but it ignores runtime engagement data exposed via settings (analytics provider, Ko-fi username, etc.), missing an opportunity to tailor prompts toward under-served categories.【F:tools/src/genprompt.ts†L39-L71】【F:src/utils/settings.ts†L1-L111】 Consider injecting top-performing tags or entity gaps into the prompt to steer ideation.
3. **Automate internal-link hint validation pre-ingest.** The validator enforces 5–8 hints with verbatim anchors, yet editors only see failures after round-tripping through ingest.【F:server/lib/postSpecValidator.js†L17-L112】【F:src/pages/admin/index.astro†L905-L918】 A small CLI (`wc lint spec.json`) that runs `validatePostSpec` without persisting would shorten iteration loops and catch anchor mismatches before writers reach for the admin UI.
4. **Record prompt lineage alongside saved Markdown.** Specs become frontmatter + sections, but the original prompt (topic, slider choices) is not persisted, which makes retrospectives on prompt effectiveness harder.【F:server/lib/specPreparation.js†L207-L248】 Save the prompt metadata in a `content/prompt-queue/shipped/` artifact or embed references in frontmatter so future audits can correlate performance with generator inputs.

### Knowledge & Entity Management
1. **Promote entity keyword extraction to shared utility.** `getEntitiesForType()` synthesizes keywords from properties and correspondences to power filters, but the logic lives only in the UI layer.【F:src/utils/entityIndex.ts†L21-L79】 Moving extraction into the ingest pipeline would let prompts or validation warn when specs reference entities lacking supporting metadata.
2. **Backfill entity stubs with richer defaults.** Stub entities receive `summary: "slug — stub entity"` and empty `properties`, which keeps the build alive but offers no guidance for editors.【F:server/lib/specPreparation.js†L120-L137】 Generate starter `properties` (e.g., blank correspondence arrays) or queue follow-up tasks automatically so the knowledge base matures alongside new posts.
3. **Expand structured data beyond ItemList.** The home page now emits `ItemList` JSON-LD for recent posts, yet downloads, curses, and entity hubs omit equivalent schemas, leaving SEO value on the table.【F:src/pages/index.astro†L12-L114】【F:src/utils/structuredData.ts†L17-L68】 Reuse `createCollectionPageSchema()` across these routes to improve discovery and clarify content types for search engines.
